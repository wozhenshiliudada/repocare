# RepoCare user guide

RepoCare investigates and maintains Git repositories with Pi, fixed authority, isolated candidates, real checks, approvals and traceable delivery. A conversation answer, form draft, repair proposal, passing candidate, published branch and merged delivery are separate states. This guide belongs to the development candidate: a catalog preview or plan is not an executable feature.

In the workbench, choose **Getting started → Open illustrated guide** to follow the quick start with screenshots in a new tab. The walkthrough is in Chinese. To read it offline, choose **Download offline ZIP**, extract it, and open `index.html`. The searchable text guide remains available in English and Chinese.

## Start and stop

Install Python 3.11+, Git, Node 22.19+ and the pinned dependencies described in SETUP.md; build the frontend for a source checkout. A wheel does not include Python, Git, Node or credentials. Docker, semantic models and CodeGraph are optional for normal use.

After installing this candidate, run `repocare setup` once, then `repocare gateway run`. Use `repocare gateway status`, `open`, `stop` and `restart` for the same configured instance. Consult `--help` for options. The gateway runs in the foreground; closing a browser does not stop it. Busy or uncertain instances are not force-killed. Keep the original state and budget when restarting.

## Conversation and help

Conversation works without a repository. Add a model in Settings, select it, create a conversation and send a question. You can ask general questions or how RepoCare works. Sending invokes your chosen model and may cost money; reading help or saving settings does not invoke a model.

Tutorial beside Settings opens, searches and downloads the same packaged Markdown the assistant reads with `get_help`. Conversation has no arbitrary file, shell, Git, maintenance, approval or publishing tools. Its separate persistent accounting does not spend or reset repository-task balances.

## Form assistance: a draft is not consent

Open the intended page and step, then explain your goal. The assistant sees only current allowed, non-secret fields. Review the old/new values and explicitly click Apply to draft. Then review the form and **click Confirm, Save or Next yourself**. A chat message is not approval.

The assistant cannot submit, advance, execute, approve costs or grant authority. Passwords, keys and consent controls require manual input. Navigation, changed fields and new steps invalidate old suggestions. Without an eligible form the assistant must ask you to open one, not invent fields.

Theme, font size, language and currently editable quiet-hour times in Settings can also be suggested as safe drafts. For example, open the assistant in Settings → General, read the current form, and ask for a dark theme and 17px font. Theme and font size are dropdowns restricted to their existing options. Applying a suggestion still requires you to click Save settings. After enabling quiet hours in Notifications, use strict 24-hour `HH:mm` times such as `22:00` and `08:00`. Values such as `9:30`, `24:00`, times with seconds or other formats cannot be applied. A suggestion containing an invalid time is rejected as a whole before any draft is written. Read the form again after changing settings categories.

Model dropdowns and the Current → Suggested comparison show readable saved configuration names, with model names where needed. These are display labels: selections, allowed options and requests retain the real saved configuration IDs. A name is never sent in place of an ID, and renaming cannot rebind an existing task. Names you supply remain in their original language.

## Settings

Use the left categories and right content. General offers Light, Dark or System in the theme dropdown, 13, 15 or 17px in the font-size dropdown, and Simplified Chinese or English. Both manual edits and assistant-applied values remain drafts until you click Save settings. Saving applies and stores them in the current browser. Closing the window does not save them. If browser storage fails, follow the on-page message; applying a setting for this visit does not establish that it was saved persistently.

Saving the interface language updates owned headings, labels and action instructions in navigation, settings, conversations, help and the core Overview, Maintenance tasks, Issues, Monitors and Queue, Memory, Delivery, Maintenance rules and Service pages. Owned controls in Connect repository and the original maintenance details follow the same selection. Switching language changes presentation only: it does not remount the maintenance controller, submit a form, confirm permission or replay a business request. Existing inputs, selections and manual confirmations are retained.

User input, user-supplied model/repository names, chat messages, model answers, repository source, diffs, commands, logs and original reports/JSON remain verbatim. Product action instructions and status labels are separate from that source content. Transient messages already generated, or original service error details, may retain the language used when they were created. Titles and bodies of historical in-app notifications already queued may also retain their original display language; new notifications use the newly saved language. This does not translate business fields, protocol enums or user records, rerun a task, or alter its record or outcome. Reopen a view if you need its latest interface wording; do not resubmit an operation to change its language.

Model settings group saved models by their exact API base URL. One provider or relay can have several models, each with independent context, output and reasoning settings. This integration uses HTTPS OpenAI Chat Completions. Use the provider's API base URL, not a dashboard, a complete `/chat/completions` URL, or an Anthropic-only endpoint.

### Compact list and per-model editing

Settings → Models groups compact provider rows by the exact base URL, with a model count and Edit/Delete actions. Edit restores saved model selections from the persistent local catalog without a network directory lookup. Fetching models only adds available choices; missing directory entries do not remove saved models. Context, output and reasoning settings expand under the SAME model row. Older versions remain in history, and collapsing a row keeps its draft. There is no second generic parameter form.

Delete asks for confirmation and removes the profile from NEW choices only. Original configuration files, bound tasks, approvals, Native records and ledgers remain. Expand Deleted models to restore. Archiving the default selects an available remaining default, or leaves no default when none remain. Edits still save immutable versions.

Unchecking a saved model lists it as pending disable. Explicit Save removes all active versions for that exact endpoint/API ID from new choices, while keeping old tasks and accounts. Fetching a directory, a missing returned ID or collapsing a row never disables anything. Unknown results retain remaining intent for explicit review, without automatic replay.

### Discover models before adding them

1. Open Settings → Models → Add model provider. Enter the Base URL and API key. A display name may contain spaces; the actual API model ID must not contain whitespace. Keep keys out of chat, Issues, screenshots and Git.
2. Leaving a completed key field, or explicitly clicking Fetch available models, reads that endpoint's `/models` directory. It does not generate text, save a model, or start maintenance. It does not query on every keystroke or retry in a loop. Adding to a saved provider can reuse its server-side key only at its original endpoint. Changing the URL requires a new key.
3. Select the models to add. The directory's ID is the actual API identifier. For example, the DeepSeek product display name DeepSeek-V4.1-Flash currently uses `deepseek-flash` at the official API; `deepseekv4.1flash` is not that ID. A relay may use different identifiers. Returned models are not automatically guaranteed to support this workbench's chat/tool protocol.
4. Configure each selected model, then save. Missing metadata must be checked against the provider's documentation. If `/models` is unavailable or the key lacks access, enter a documented ID manually. Finding an ID, saving its configuration and successfully generating a response are three separate checks.
5. Multiple selections save sequentially. Keep the saved and unsaved portions visible; on an unknown result, refresh and inspect before another submission. No automatic generation follows saving.

### Token lengths

Context capacity includes input, history and output in one request. Maximum output limits one response, not the whole task. Tokens are not character counts. Inputs accept decimal `k/K/m/M`: `128k=128000`, `1M=1000000`, `1.5m=1500000`. Prefer exact directory integers because provider marketing units may differ. Conversion must produce an integer; negative values and exponent notation are rejected.

Explicit context must be at least 4096; output must be positive and below context, within safe integer representation. There is no universal 128000-output ceiling. A declared 1000000 output is allowed when the model and context actually support it. The official DeepSeek directory read on 2026-10-31 returned 1048576 context and 393216 maximum output: 1M context does not mean 1M output. Short connectivity probes and compaction have their own purpose budgets. Message bytes, Native size and timeouts remain separately bounded.

### Define available reasoning levels per model

Expand a model to configure the reasoning protocol, default level and level-to-API-value table. The default table lists `off / low / medium / high / xhigh / max / minimal`. Delete unnecessary levels or add deleted levels back. Repository and assistant selectors offer only the saved table's levels.

Labels and API values need not match. DeepSeek mappings can use `minimal→low`, `medium→high`, `xhigh→high`. DeepSeek off sends `thinking.type=disabled`; enabled levels use `reasoning_effort` according to the table. OpenAI-compatible off mapped to `none` requires support for that value. A blank API mapping omits that parameter and uses the provider default; it does not guarantee thinking is disabled. Choose no reasoning parameters for services that do not accept them. Seven labels do not establish seven distinct provider-supported intensities.

Changing a model, endpoint, key, lengths or reasoning table saves an immutable version. Existing tasks keep their original version, approvals and account. Identical complete configurations reuse their ID. Profiles without explicit reasoning fields keep their historical behavior. Changing the default does not rebind existing monitors.

### Compact model and thinking card below the input

Both maintenance and assistant composers show one compact model/depth control below the text input. Open it to adjust a discrete slider using ONLY configured reasoning levels. Click the model name inside the card to open a searchable list with the current model checked. Arrow/Home/End keys adjust the slider; Escape or clicking outside closes the card. Changes remain staged until applied.

An Apply action appears only for a changed choice. Assistant changes create a linked continuation; repository choices prepare the corresponding persistent model context. No generation follows selection, creation or application: only manual Send starts a model request. Original tasks and unknown accounting remain intact.

### Choose separately for each repository and the assistant

On repository A's task page, choose a model and one of its saved reasoning levels, then apply to new tasks. This only prepares or reopens that repository's persistent model context; it does not call the model. Repository B can use another model and level without changing A's existing tasks. Returning to a previous configuration reuses its original balance. An executing call and existing task approvals/recovery are not transparently migrated.

The repository-free assistant also offers model and reasoning selectors. Switching an existing conversation creates a linked continuation and retains the original session, Native file and ledger. Successful historical text is read-only context; old proposals and approvals are not new permissions. Only the next manually sent message calls the new model. Oversized continuation history is explicitly blocked instead of silently truncated.

Saving provider models adds them to the catalog; it does not automatically replace the current conversation or default. Reopen Settings → Models → that provider to see persisted selections without re-entering a key. To use one, click the model below the assistant input, choose the new model/depth, and apply a linked continuation. Maintenance tasks choose separately below their input. Only an explicit Set default action changes the new-session default. An unchanged edit/save creates no duplicate configuration or allowance.

For an invalid-model error, check the exact directory ID; for authentication, check the key's endpoint and access; for unsupported parameters, check lengths, reasoning protocol and mapping. A strictly verified terminal failure counts actual requests and releases unused reservation. Missing receipts, interrupted processes or unknown consumption remain unknown without automatic replay. Upgrading does not clear historical unknown reservations, and reserved requests do not prove that many calls were actually made.

Notifications cover pending approvals, completion, failure and service changes. Choose in-app, desktop and sound, with quiet hours. Browser permission requires explicit action. Quiet hours suppress desktop/sound while retaining in-app records. Browser notifications are not a background messaging service after the app is closed.

Quiet hours use the computer's local time and may span midnight; equal start and end times mean all day. Entered or assistant-applied times remain drafts until saved. The assistant never requests desktop notification permission or supplies consent for model costs, maintenance or publication.

## Connect a repository

Connect an existing local Git repository or choose GitHub using your credential manager. Do not paste credentials into Issues or prompts. Preview and analyze before confirming maintenance rules. Preserve dirty work. Rules bind editable/read-only scope, checks, budgets and manual/autonomous authority; a model or Issue cannot expand them.

## Pages and maintenance

- Overview: navigate real tasks and next steps; summary cards are not delivery proof.
- Maintenance tasks: enter clues when available, or choose “Configure automatic checks without a problem description” to set directory maintenance in Monitoring & follow-up. A manual description is not required for automatic failure discovery. Inspect diagnosis, baseline, diff, risk and checks. New-task model selection does not transfer old tasks. Return to their original workspace for old approvals and balances.
- Issue workflow: issue type, maintainer intake and permissions differ. `ready-for-agent` is intake, not command/cost authority. Verified candidates await delivery, not automatic Issue closure.
- Monitoring and inbox: observe approved branches and sources. Events, model grants and autonomous grants differ. Existing monitors keep their original model/budget. Duplicate, stale and unknown work is not silently replayed.
- Memory and knowledge: historical evidence, reviewed experiences and optional structure are references. Revalidate sources and current tests; history is not authority or proof of current correctness.
- Delivery and acceptance: packaging, local branch publication, push, PR, merge, post-merge checks and Issue closure have separate controls. Verify exact SHA, run, attempt and Jobs. Local/synthetic results are not remote CI success.
- Maintenance settings: inspect scope, model, environment and budgets; do not reset state to bypass guards.
- Service management: inspect installation, drift, activity and safe shutdown. Local readiness is not a model response; an explicitly confirmed connectivity probe makes a metered request.

## Checks, recovery and budgets

### Automatic maintenance without a problem description

1. Connect the repository and open Monitoring & follow-up. Read the current repository preview if needed. Maintenance settings also links to automatic commit maintenance; its other controls mainly cover Issue rules and original task allowance.
2. Configure readable/writable directories and allowed check families. The system finds concrete implementation files and check commands. Authorize isolated code execution and dependency preparation separately, then preview and confirm the rules.
3. When checks reproduce a failure, preview its repair scope and original allowance. Business acceptance cases are optional for an existing failure; leave that form empty and proceed directly to repair consent.
4. To handle future commits automatically, explicitly confirm a time-limited model grant and mode. Manual mode produces a proposal requiring approval; autonomous mode prepares an isolated candidate within the approved scope. Existing failures are not silently replayed. Model grants pause after a restart.
5. New commits are observed on the monitor schedule. “Check now” respects the same low-frequency guard; wait when the interval has not elapsed. Uncommitted edits are not new commits.
6. Verify actual candidate checks and the diff. Packaging, local branch publication, push, PR, merge and acceptance are separate. Pause retains original history, used requests and unknown reservations.

This path can discover failures through repository checks; green checks do not prove the absence of hidden logic errors. Missing verification should be reported or clarified rather than turned into fabricated repair success.

Check commands run tests, type checks or verifiable validation. JSON arguments separate program and arguments, e.g. `["{python}","-m","unittest","discover","-s","tests","-v"]`. Discover them from project instructions/CI. No tests or exit zero alone cannot prove correct behavior.

Compare baseline/candidate in equivalent environments. Rollback affects only the agent's own isolated edits; source work and evidence remain. Manual mode requires current approval. Autonomous mode stays within preauthorized rules.

Requests, tokens and money differ. A task can make many calls. Unknown reservations remain held until original evidence is reconciled; refresh, restart or new conversations do not refund them. Lost receipts require read-only reconciliation, not repeated submission. Code updates need a safe restart, not browser refresh.

## MCP for another agent

This candidate provides `repocare mcp` over standard stdio through the original local gateway. Defaults are read-only service/workspace/operation/tutorial access. Explicit planning permission can create a proposal through the original Pi/controller/budget. The user still reviews it in WebUI.

There are no approval, publish, merge, arbitrary HTTP or shell tools. Another agent's text is not consent. See the version's MCP instructions for exact tools/configuration. Never paste gateway capability tokens into model messages.
